Concept

メモリはどこにある？

通常の DDS message 用 allocation と、大きな payload 用の shared allocation は別物です。 Publisher と Subscriber は payload をコピーし合わず、OS が管理する同じ backing object を map します。

rosidl::Buffer の storage backend として働きます。通常の ROS message の field と小さな descriptor は RMW/DDS が配送し、buffer payload は backend が管理する別 allocation に残ります。

Under the hood

OS に合わせて、同じ体験を

Lx

Linux

anonymous memfd

Publisher が匿名の memfd を作成し、Unix domain socket 経由の SCM_RIGHTS で FD を受信 process へ渡します。

  • payload 自体に filesystem 上の名前は不要
  • 最初の import 後は mapping cache を再利用
  • 最後の FD / mapping が消えると kernel が回収
W

Windows

named file mapping

Publisher が page-file-backed mapping を作成し、Subscriber は descriptor 内の session-local name から同じ object を開きます。

  • Local\\ namespace で同一 session 内共有
  • random nonce で stale object との衝突を防止
  • 最後の handle が閉じると OS が回収
↻

Both platforms

pool と世代チェック

固定サイズの block を pool で再利用。publication ごとの ipc_uid と reader count で、古い descriptor や読み取り中の上書きを防ぎます。

  • 対応 endpoint は同一 host・同一 user
  • Windows は同一 login session も必要
  • 条件不一致では通常の CPU buffer path

Getting started

ROS 2 Lyrical workspace に追加

この backend は ROS 2 Lyrical で導入された rosidl::Buffer を対象とします。現時点では source build を想定しています。

  1. 01
    ROS 2 Lyrical

    rosidl::Buffer と backend API を含む環境。

  2. 02
    Linux または Windows

    同じ host・user の process 間で利用します。

  3. 03
    colcon / rosdep

    通常の ROS 2 source workspace として build。

Linux / bash 
mkdir -p ~/ros2_lyrical_ws/src
cd ~/ros2_lyrical_ws/src
git clone -b lyrical \
  https://github.com/dskkato/shmem_buffer_backend.git

cd ~/ros2_lyrical_ws
rosdep install --from-paths src --ignore-src -r -y
colcon build --symlink-install
source install/setup.bash

Windows では ROS 2 の Developer Command Prompt で build し、call install\setup.bat を実行します。

API

C++ と Python、同じ lifecycle

allocate → scoped write → publish → scoped read。handle / context を閉じるまで pointer や view が有効です。

Publisher
#include "shmem_buffer/shmem_buffer_api.hpp"

sensor_msgs::msg::Image msg;
msg.data = shmem_buffer::allocate_buffer(byte_count);

{
  auto write = shmem_buffer::from_output_buffer(msg.data);
  std::memcpy(write.get_ptr(), pixels, byte_count);
} // write を finalize

publisher->publish(msg);
Subscriber
void on_image(
  sensor_msgs::msg::Image::ConstSharedPtr msg)
{
  auto read =
    shmem_buffer::from_input_buffer(msg->data);

  process_pixels(
    read.get_ptr(),
    msg->data.size());
} // read lease を解放
Write
import numpy as np
from shmem_buffer import allocate_buffer, write_buffer

buffer = allocate_buffer(1920 * 1080)
with write_buffer(buffer) as view:
    image = np.frombuffer(view, dtype=np.uint8)
    image[:] = pixels
    del image

message.data = buffer
Read
import numpy as np
from shmem_buffer import read_buffer

view = read_buffer(message.data)
image = np.frombuffer(view, dtype=np.uint8)
process(image)
i
read view の lifetime は自動管理

read lease は派生した NumPy array / memoryview に保持され、最後の view が破棄された時に自動で解放されます。write view は with の scope 内だけで使用してください。

i
受信側の CPU buffer も読める

from_input_buffer() / read_buffer() は非 shared buffer を同期 copy で promote できます。この場合は inter-process zero-copy ではありません。
